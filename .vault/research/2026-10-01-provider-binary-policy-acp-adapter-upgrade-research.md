# `provider-binary-policy` research: `acp adapter upgrade`

Does bumping `@agentclientprotocol/claude-agent-acp` from the locked `0.59.0` (SDK `0.3.207`, CLI `2.1.207`, `@agentclientprotocol/sdk@1.2.1`) to the npm-latest `0.84.0` (SDK `0.3.284`, CLI `2.1.284`, `@agentclientprotocol/sdk@1.5.1`, `zod@4.6.5`, `diff@9.0.0`) change anything our usage depends on. Conclusion: no breaking wire or API incompatibility was found against the production code paths this project exercises (confirmed both by diffing the published sources and by a live `initialize` + `session/new` probe against the real 0.84.0 package). The permission-mode catalog changed in a way that is compatible with the pinned `default` posture but forecloses the `2026-10-01-tool-permission-model-adr` Rationale's stated `dontAsk` reconsideration path. The adapter gained a large number of new capabilities (native ACP subagent sessions, async-task reporting, file-change checkpointing, elicitation, provider routing, session notices/titles/timing, a new `effort` session option) that are all opt-in behind `clientCapabilities` fields this project's `initialize` call does not send, so none of them changes observed behaviour today. One capability is unconditional and directly actionable: the terminal `session/prompt` response now carries per-turn and per-model token usage, closing the Claude-lane half of the `token-accounting-gaps` finding. Not investigated: a real model turn (no credentials on this host, and the task scope excludes sending prompts), the Compose/container image's own Node and Claude CLI versions, the desktop capsule's bundled Node asset version, and the full `@anthropic-ai/claude-agent-sdk` TypeScript source beyond the `.d.ts` surfaces and the two vocabulary tables (`filePatternTools`, `PermissionMode`, `HookEvent`, `hooks` option shape) diffed directly.

## Findings

### (a) Breaking - none found against current usage

No wire shape, option field, or executable path this project depends on was removed or renamed between `0.59.0` and `0.84.0`. Specifically verified unchanged: the npm package's `bin`/`main` fields and the `dist/index.js` entry point our launcher resolves (`package.json` of both versions; our path is built at `src/vaultspec_a2a/providers/_factory_commands.py:31-38,165-171`); the `session/fork` method name our `fork_session()` calls (`acp_chat_model.py:1025-1042`) is registered identically in both versions' `onRequest(methods.agent.session.fork, ...)` chain (old `dist/acp-agent.js:5458`, new `dist/acp-agent.js:8172`); the `PermissionOptionKind` enum (`allow_once`, `allow_always`, `reject_once`, `reject_always`) our `_is_approval_option`/`_is_always_option`/`_offered_refusal_option_id` match against (`_acp_rpc_handlers.py:374-417,453-472`) is byte-identical in the `@agentclientprotocol/sdk` schema at `1.2.1` and `1.5.1` (`schema/schema.json` `$defs.PermissionOptionKind`); the SDK's `filePatternTools` vocabulary our `CLAUDE_PATH_RULE_TOOLS` mirrors (`_claude_tool_policy.py:113-115`) is identical text in `@anthropic-ai/claude-agent-sdk@0.3.207` and `@0.3.284` (`sdk.mjs`, grep `filePatternTools`); `PermissionMode` stays `'default' | 'acceptEdits' | 'bypassPermissions' | 'plan' | 'dontAsk' | 'auto'` in both SDK versions' `sdk.d.ts`; the `Options.hooks` shape (`Partial<Record<HookEvent, HookCallbackMatcher[]>>`) that the unproven `2026-10-01-tool-permission-model-plan` `P01.S01` probe targets is unchanged, and `PreToolUse` remains a `HookEvent` member in both (`sdk.d.ts` `HOOK_EVENTS`); the Node floor `engines.node: ">=22"` is unchanged (both `package.json`s) and already satisfied by this project's pinned `26.8.1` (`.node-version`, `package.json` `engines.node`); `npm audit` against a fresh `0.84.0` install reports zero known vulnerabilities and `npm audit signatures` verifies registry signatures on all 106 resolved packages (this session, 2026-10-01). The live probe (below) completed a full `initialize` + `session/new` round trip against the real `0.84.0` package with zod `4.6.5` validating both our request and the adapter's response, which is the strongest available evidence that the request/response shapes this project sends are still accepted.

### (b) Behaviour change - the advertised permission-mode catalog changed shape, compatibly with the pinned posture

Live probe evidence (this session): spawning `node dist/index.js` from a fresh `npm install @agentclientprotocol/claude-agent-acp@0.84.0` and driving `initialize` then `session/new` over stdio JSON-RPC returned `agentCapabilities.agentInfo.version: "0.84.0"` and a `session/new` result whose `modes.availableModes` is exactly `[{id: "default", name: "Manual"}, {id: "acceptEdits"}, {id: "plan"}, {id: "auto", name: "Auto", description: "Claude handles permission decisions"}, {id: "bypassPermissions"}]` - `dontAsk` is absent. This matches the adapter source directly: `buildAvailableModes()` (`@agentclientprotocol/claude-agent-acp@0.84.0 dist/session-mode.js:204-246`) composes exactly `default`, `acceptEdits`, `plan`, `auto`, and `bypassPermissions` (the last only when bypass is allowed); `dontAsk` is never added to the list, even though `parseMode()` three lines below still accepts the string `"dontAsk"` as a program­matically settable value and the mode-alias table in `permissions/modes.js:4-17` still normalizes the word. `0.59.0` has no equivalent source file; the current pinned adapter composes its mode list differently (not diffed line-for-line, since `0.59.0`'s mode-building code is not factored into a single function the way `0.84.0`'s is, but the `2026-10-01-tool-permission-model-adr` Problem Statement and Rationale already establish that the `0.59.0`-era CLI documentation described `dontAsk` as an offered mode). Effect on us: none today. `_pin_autonomous_permission_mode` (`_acp_session.py:611-678`) only requires `AUTONOMOUS_PERMISSION_MODE = "default"` (`_claude_tool_policy.py:97`) to be a member of `availableModes`, which it still is, confirmed live. Decision-relevant effect: `2026-10-01-tool-permission-model-adr`'s Rationale states "the posture is recorded with its reconsideration condition" and the Considered-options section writes "`dontAsk` once a hook carries the policy" as the target state once `P01.S01`'s hook-threading probe succeeds. On `0.84.0` that target state is unreachable: `session/set_mode` and `session/set_config_option` both validate the requested mode against `availableModes` (`session-mode.js:33-38,113-118`) and refuse a mode that is not listed, so even a fully-proven `PreToolUse` hook could never move this project onto `dontAsk` on the upgraded adapter. This needs the ADR owner to correct the reconsideration-condition prose (an amendment, not a new decision): `dontAsk` is not merely undesirable-until-proven, it is now unofferable by the adapter the project would be pinning to.

### (b) Behaviour change - a new `auto` mode exists and is available whenever `bypassPermissions` is

`buildAvailableModes()` (`dist/session-mode.js:230-236`) always includes `{id: "auto", name: "Auto", description: "Claude handles permission decisions"}` regardless of `allowBypass`; the live probe confirms it is offered. `auto` mode runs a model classifier inside the CLI that can approve or deny tool calls without consulting our `canUseTool`/`session/request_permission` rung at all for calls it judges safe (public documentation, not independently verified against source: Anthropic's "Auto mode" blog post and `code.claude.com/docs/en/agent-sdk/permissions`, both fetched via web search this session). This project never requests `auto`: `_pin_autonomous_permission_mode` only ever asks for `AUTONOMOUS_PERMISSION_MODE` (`"default"`), and `_select_config_option` fails loudly if the adapter's confirmed value differs from the requested one (`_acp_session.py:306-322`), so a session could not silently end up in `auto` through our own code. The only path into it would be an ambient `permissions.defaultMode: "auto"` in a settings file the SDK's `SettingsManager` resolves before our pin lands (see next finding); our pin-and-verify exchange runs after session creation and overrides that unconditionally, exactly as it already does for `acceptEdits`/`bypassPermissions` today. No code change identified as necessary; flagged here because it is new attack-surface vocabulary a reviewer of the mode-pinning code should recognise.

### (b) Behaviour change (confirmed benign, pre-existing mechanism) - the adapter's own `SettingsManager` and managed-policy env resolution run unconditionally, independent of our `settingSources: []` session option

`0.84.0` factors settings resolution into a new `SettingsManager` class (`dist/settings.js`) that watches `~/.claude/settings.json`, `<cwd>/.claude/settings.json`, `<cwd>/.claude/settings.local.json`, and a platform managed-settings path (`/etc/claude-code/managed-settings.json` on Linux) and resolves them through the SDK's `resolveSettings`, applying `filterEscalatingDefaultMode` to strip an escalating `permissions.defaultMode` from a repo-committed source (`settings.js:18-27,89-103`). This governs the session's *initial* mode before our pin: `resolvePermissionMode(creationOpts.permissionMode ?? settingsManager.getSettings().permissions?.defaultMode, ...)` (`acp-agent.js:6489`). Our `_meta.claudeCode.options.settingSources: []` (`_acp_session.py:103`, documented at `claude_session_options` docstring `:89-97`) controls the CLI's SDK-level settings surface for the running query, which is a *different* mechanism from this adapter-level `SettingsManager`; the two do not currently appear to be made to agree by one override. In practice this is not a new gap: `_pin_autonomous_permission_mode` already treats whatever mode the session reports after creation, including one resolved from an ambient `permissions.defaultMode`, as untrusted, and overwrites it with a verified `session/set_config_option` call before any prompt is sent (`_acp_session.py:611-678,769-771`). This is the same design the `2026-07-15-agent-harness-provisioning-adr` 2026-08-02 amendment already documents for the parallel MCP-surface problem. No action proposed; recorded because `SettingsManager` is new machinery performing a job `0.59.0` already did inline (see `claudeCliPath`/settings read referenced in `0.59.0`'s `dist/index.js`), so a reviewer diffing stderr or behaviour should expect to see new `[session/create] phase=settings` timing lines (from the new `session-timing.js` module) that did not exist before.

Separately, the *managed-policy* env-injection step - `resolveSettings({settingSources: []})` read once at adapter process start and merged onto `process.env` before any SDK call (`dist/managed-policy.js:18-30`) - is not new: `0.59.0`'s `dist/index.js:45-48` performs the identical read and the identical `process.env[key] = value` merge inline. The only change is robustness: `0.59.0`'s inline version has no `try`/`catch` around the `await resolveSettings(...)` call, so a malformed or unreadable `managed-settings.json` on the host would throw an unhandled rejection at adapter start-up and crash the whole Claude/Z.ai lane before `initialize` is ever reached. `0.84.0`'s `applyManagedPolicyEnv` wraps the same call in a `try`/`catch` that logs to stderr and continues with no policy env on failure (`managed-policy.js:18-27`). This is a genuine, if narrow, latent-fragility fix inherited for free by the bump (see Opportunity below); it is not a new behaviour change this bump introduces, since the underlying env-merge semantics - and the risk that a host-level `managed-settings.json` could inject env vars into the spawned CLI's process outside this project's `resolve_env_vars` allowlist (`src/vaultspec_a2a/workspace/environment.py:146-161`) - already exist on `0.59.0` today. Not investigated: whether this host class (Compose worker image, desktop capsule, checkout) ever carries a `managed-settings.json`; the finding is recorded for whoever next audits credential-injection surfaces, not raised as a new Step here.

### (c) Security-relevant - every genuinely new capability class is gated behind a `clientCapabilities` flag this project's `initialize` call does not send, and stays inert

The new modules named in the task brief - `acp-subagents`/`native-subagents` (native ACP subagent sessions), `async-tasks` (AIR-reported background task lifecycle), `file-change-audit` (file checkpointing), `elicitation` (user-dialog forwarding), `context-compaction` (structured compaction reporting) - are each constructed only when the corresponding client capability is present. Verified directly: `createElicitation` is invoked only when `this.clientCapabilities?.elicitation?.form` or `.url` is truthy (`acp-agent.js:5775,5820,6509-6510`), and when it is false the adapter itself adds `AskUserQuestion` to the session's `disallowedTools` (`acp-agent.js:6515`) rather than leaving it reachable; `enableFileCheckpointing: true` is only set on the SDK options when `supportsAgentFileChangeReport(this.clientCapabilities)` is true (`acp-agent.js:6534,6605`); the AIR-only metadata that would make subagent/async-task notifications carry the `nativeSubagentSessions`/`asyncTasks` advertised capabilities is gated on `this.toolCallCapabilities.air.client` (`acp-agent.js:1298-1310`), itself derived from an `air`-namespaced `_meta` client capability block this project does not send. Our `initialize` call (`_acp_session.py:386-417`) sends only `fs.{readTextFile,writeTextFile}`, `terminal`, and the `_meta: {"terminal-auth": true, "terminal_output": true}` block; it declares no `elicitation`, no `air`, no `session.compaction`, no `agentFileChangeReport`. Consequence: none of these new surfaces changes what the model can do or what gets reported to us until this project deliberately opts in. This directly narrows the task brief's security framing - these are real new capabilities in the package, but they are not live risks of the bump itself for an unmodified client.

### (c) Security-relevant (confirmed pre-existing, not new) - async/background Bash execution and in-process subagents already existed at the SDK level before this bump

`run_in_background` is present on the Bash tool schema in both `@anthropic-ai/claude-agent-sdk@0.3.207` and `@0.3.284` (`sdk-tools.d.ts`, grep count 2 in each). The `async-tasks`/`native-subagents` adapter modules add ACP-level *reporting* of task lifecycle (`task_started`, `background_tasks_changed`, deferred turn settlement while a spawned subagent is still live - `acp-agent.d.ts` `Turn.spawnedTaskIds`/`deferredSettle` comments) but do not change the authorization boundary: a background Bash call or a `Task`/`Agent` subagent spawn is still one `canUseTool`/`session/request_permission` decision on the tool named in the call, decided by the same `on_request_permission`/`_autonomous_option_id` path as any other tool (`_acp_rpc_handlers.py:540-587,590-702`) - it is not pre-approved or floor-approved by this project's composed sets (`Task`/`Agent` is in neither `CLAUDE_FILE_WRITE_TOOLS`, `CLAUDE_TERMINAL_TOOLS`, nor the native read floor), so an autonomous run already refuses an uncovered subagent-spawning call today, before and after the bump. The architectural consequence of this project's own design (`2026-10-01-provider-binary-policy-adr` D5: one spawn and one `session/new` per Claude call, killed at turn end) is that any backgrounded shell command the model starts is torn down with the process at `_cleanup_session`/`_kill_process_tree` (`acp_chat_model.py:835-919`) regardless of adapter version; this was already true on `0.59.0` since `run_in_background` already existed there. Not a bump effect; recorded because the task brief asked for an explicit security read on this class.

### (d) Opportunity - the terminal `session/prompt` response now carries per-turn and per-model token usage, unconditionally

`turnOutcome()` (`dist/acp-agent.js:7097-7103`) attaches `usage: {inputTokens, outputTokens, cachedReadTokens, cachedWriteTokens, totalTokens}` and `_meta.quota: {token_count: {...}, model_usage: [{model, token_count: {...}}]}` to every `session/prompt` result, unconditionally (no client capability gates it); `quotaTokenCount()` (`:7132-7141`) reports `totalTokens`, `inputTokens`, `cachedInputTokens`, `cachedWriteTokens`, `outputTokens`, and a structural `reasoningOutputTokens: 0` (Claude bills thinking inside output tokens, so this is always zero but present for cross-agent shape parity with codex-acp, per the adjacent comment). This is confirmed as new relative to `0.59.0` by the published changelog entry "v0.71.0: report per-model token usage on prompt responses" (`raw.githubusercontent.com/agentclientprotocol/claude-agent-acp/main/CHANGELOG.md`, fetched this session) and by the absence of any `quota`/`modelUsage`/`accumulatedUsage` machinery in the installed `0.59.0` `dist/acp-agent.js` (not present as a module at all in that version's file list). This closes exactly the half of `token-accounting-gaps` the audit records as still open: "Status: fixed in P05.S32 ... Codex maps cache-read, cache-creation, and reasoning tokens ... but `_turn_token_usage` keeps only input/output/total" is the Codex half; the finding's own title says "ACP lanes report none" (`.vault/audit/2026-09-24-architecture-review-audit.md:203-205`), and the companion finding `prompt-order-vs-cache` is explicitly recorded as "size unmeasured because ACP reports no usage" (`:201`). `_turn_token_usage` (`src/vaultspec_a2a/graph/nodes/worker.py:634-658`) already reads LangChain's generic `usage_metadata` off the final `BaseMessage` and is provider-agnostic; it needs nothing new to start working for the Claude lane once the ACP layer populates `usage_metadata` on the terminal chunk/message. The natural integration point is `_finish_prompt_response` (`src/vaultspec_a2a/providers/_acp_protocol.py:284-308`), which already reads `result.get("stopReason")` off the same `result` object that will carry `usage`/`_meta.quota` and currently discards everything else; `_yield_chunks` (`acp_chat_model.py:745-776`) is where a final usage-bearing chunk would need to be assembled before the generator ends. No new decision needed: this is a direct extension of the existing `CostPort`/`record_usage` seam (`src/vaultspec_a2a/graph/protocols.py:93-126`, `src/vaultspec_a2a/worker/cost_port.py`) already used by the Codex lane. Scope caveat: `usage`/`_meta.quota` only appear on the terminal `session/prompt` response; a mid-stream `usage_update` session notification type already exists in the `@agentclientprotocol/sdk` schema at both `1.2.1` and `1.5.1` (`schema/schema.json` `$defs.SessionUpdate` enum) but was not verified to be emitted by the Claude adapter mid-turn, only the terminal shape was confirmed by source.

### (d) Opportunity - managed-policy settings resolution is now fault-tolerant at adapter start-up

As established above, `0.59.0`'s inline managed-policy env read has no error handling and would crash the adapter process on a malformed or transiently unreadable `managed-settings.json`/MDM source before `initialize` is ever reached; `0.84.0`'s `applyManagedPolicyEnv` (`dist/managed-policy.js:18-31`) catches and logs instead. This is a free robustness improvement from the bump on any host where such a managed/MDM settings source could exist or become transiently unreadable (`EINTR`/`EMFILE`/`EAGAIN`, per the function's own doc comment). No action needed; cited as one of the concrete reasons to prefer landing the bump over staying pinned, for the ADR/plan's rationale section if the orchestrator wants one.

### (d) Opportunity, needs a new decision if pursued - native `providers/set`/`providers/list`/`providers/disable` ACP methods

`unstable_setProvider`/`unstable_listProviders`/`unstable_disableProvider`, wired to wire methods `providers/set`, `providers/list`, `providers/disable` (`dist/acp-agent.js:1608-1672,8180-8182`), are genuinely new: grep for `unstable_setProvider`/`providers\.` in the installed `0.59.0` `dist/acp-agent.js` returns nothing. They let a client redirect the session's LLM backend (`apiType`, `baseUrl`, `headers`, optional `vertex` block) without env-var injection. This project currently routes Z.ai through raw `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` env vars built by `_build_zai_env` (`src/vaultspec_a2a/providers/_factory_commands.py:67-86`) and injected as `self.env_vars` overlay (`acp_chat_model.py:136-145,504-511`). Replacing that with an ACP-level `providers/set` call would change the ACP wire contract this project uses, which `2026-08-02-llm-context-provider-abstraction-acp-v1-client-wire-adr` governs; adopting it is a new costly decision (a new or amended wire-contract ADR), not something to do inside this bump. Recorded as an opportunity only; no Step proposed to adopt it.

### (d) Opportunity, needs a new decision if pursued - ACP elicitation as a candidate clarification transport

`session/create_elicitation` (form/url modes) is the ACP-level channel the SDK's `AskUserQuestion` built-in and MCP `onElicitation` requests route through when a client declares `clientCapabilities.elicitation.{form,url}` (`dist/elicitation.d.ts` header comment; gating confirmed above). This project's clarification mechanism is governed by the `clarifications-are-typed-interrupts` rule, whose "one pause mechanism" invariant requires every mid-run question to go exclusively through the checkpointed LangGraph `interrupt()` with a bounded typed payload, and explicitly forbids a side channel. Wiring ACP elicitation as a *transport underneath* that one mechanism (never as a second pause path) is conceivable but is itself a new decision with its own wiring-is-proven obligation under that rule; it is named here only because the task brief asked about it, not proposed as a Step.

### (e) Irrelevant - additional confirmed-unchanged or inert points

`zod` `^3.25||^4` to `4.6.5` and `diff` (new direct dependency, `9.0.0`) are internal to the adapter's own request/response validation and diff-rendering; this project parses no diff content (`grep` for `"diff"`/`oldText`/`newText` across `worker.py` and the providers package returns nothing) and the live probe exercised zod's validation successfully on both our `initialize`/`session/new` payloads and the adapter's replies. `ReadTextFileRequest`'s shape (`sessionId`, `path`, `line` 1-based, `limit` lines, no `offset` field at all) is byte-identical between `@agentclientprotocol/sdk@1.2.1` and `@1.5.1` (`schema/schema.json` `$defs.ReadTextFileRequest`), so this is not a bump effect (see the pre-existing-debt note below). `SessionUpdate`'s enum gained exactly three new variants between the two SDK versions - `notice`, `compaction_update`, `compaction_summary_chunk` - and the other apparently-new-looking ones (`config_option_update`, `session_info_update`, `usage_update`, `plan_update`, `plan_removed`) were already present at `1.2.1`. None of the three new variants, nor any of the pre-existing-but-unhandled ones, breaks `handle_session_update` (`src/vaultspec_a2a/providers/_acp_protocol.py:452-492`): the function is a sequence of `if u_type == X: ...; return` checks with no final `else`, so any unrecognised `sessionUpdate` value - old or new - is silently and safely ignored. The same catch-all shape in `dispatch_packet` (`_acp_protocol.py:214-242`) ignores any server-to-client notification method it does not recognise (for example the new connection-scoped `_auth/status_update` push the live probe observed immediately after session creation: `{"jsonrpc":"2.0","method":"_auth/status_update","params":{"authStatus":{"kind":"none","label":"Not logged in"}}}`). This is a deliberate, confirmed compatibility property, not an accident: new unsolicited notifications from an upgraded adapter cannot crash this project's dispatch loop, though they also will not be acted on until explicitly handled (see the `session-titles`/`session-notices`/`auth-status` opportunity note below, which is minor enough not to warrant its own Step). `Bash`'s permission-request `title` is the literal shell command text (`BashReporter.toolUse`, `dist/tool-calls/reporters/bash.js:4-10`) and `Read`/`Write`/`Edit`/`Grep`/`Glob`'s titles are human prose with the path or pattern baked in (`dist/tool-calls/reporters/read.js:15`, `file-edit.js:12,75`, `search.js:11,17,48`) - this is byte-for-byte the same shape the installed `0.59.0` `dist/tools.js:38,63,76-99,105-124,126-141,142-` already produces, confirmed by direct comparison; it is not a bump effect. The new `effort` session config option (`session-effort.js`, confirmed live: `configOptions` includes `{id: "effort", category: "thought_level", options: [default, low, medium, high, xhigh, max]}`) and the live-observed model catalog (which now lists a `"claude-fable-5-1"` entry alongside `sonnet`/`opus`/`haiku`) are additive `configOptions`/model-catalog entries our generic `_config_options`/`_select_desired_model`/`_select_desired_config_options` readers (`_acp_session.py:161-343`) tolerate without modification, since they only act on config ids this project explicitly names in `config.desired_config_options`; model-catalog drift itself is `2026-08-02-provider-model-catalog-adr`'s domain, not this record's.

### Pre-existing, not a bump effect, but corroborating already-tracked debt

Two things surfaced while diffing titles and file-read params are real gaps in current production code, confirmed identical on `0.59.0` and `0.84.0`, and already owned elsewhere:

First, `on_fs_read_text_file` (`src/vaultspec_a2a/providers/_acp_rpc_handlers.py:705-745`) reads `offset`/`limit` as byte counts, but the ACP protocol's `fs/read_text_file` request has never carried an `offset` field at either `1.2.1` or `1.5.1` - only 1-based `line` and a line-count `limit` (`@agentclientprotocol/sdk` `schema/schema.json` `$defs.ReadTextFileRequest`, identical in both versions). This is exactly the gap `2026-08-02-llm-context-provider-abstraction-acp-v1-client-wire-adr` names ("Replace byte-offset read handling with one-based line selection and line-count limiting") and its open `2026-08-02-llm-context-provider-abstraction-plan` Step `P01.S01` ("Validate ACP v1 session ownership and replace byte-offset filesystem reads with one-based line pagination", unchecked, next per `vaultspec-core status`) already owns. The bump neither creates nor fixes this; it is recorded here only because it was independently reconfirmed against the exact target SDK version (`1.5.1`) this upgrade would bring in, which may be useful corroboration for prioritising that already-open Step.

Second, the native read floor's confinement check (`_floor_call_is_confined`/`_autonomous_option_id`, `_acp_rpc_handlers.py:519-587`) matches the permission request's `title` against the bare strings `"Read"`/`"Grep"`/`"Glob"` (`_native_read_tools`, which returns `_CLAUDE_NATIVE_READ_TOOL_NAMES = NATIVE_READ_TOOL_NAMES = ("Read","Grep","Glob")`), but on both adapter versions the title for these tools is always prose carrying the path or pattern (`"Read " + path + limit`, `"Find \`path\`"`, lowercase `"grep ..."` - confirmed identical in `0.59.0` `dist/tools.js` and `0.84.0` `dist/tool-calls/reporters/{read,search}.js`), never the bare tool name. The bare-name branch is therefore unreachable on either version; a native-floor call that reaches the rung at all falls through to the final `return _refusal_option_id(options)` regardless of whether it is actually confined to the bound project. The net observable behaviour (an out-of-workspace native-floor call is refused) is accidentally correct on both versions because the fallback is a refusal, but the "approve when confined" branch this project's own comments describe as the point of the check has never been exercised at the rung on either version. This corroborates, rather than duplicates, two already-open audit findings owned by `2026-10-01-tool-permission-model-plan`: `grep-pre-approved-host-wide`'s residual note ("that in-workspace Grep proceeds unprompted rests on the pinned CLI's working-directory posture and has no live proof yet; if it does not, Grep degrades to refused rather than to host-wide") and `claude-path-rule-tools-include-unconsulted-names` (owned by `P07.S21`). Not a bump effect; no new Step proposed here, since the existing Steps already cover the territory and a title-matching rewrite is an implementation detail for whoever executes `P01.S02`/`P07.S21`.

### What was not investigated / could not verify

No live model turn was run on either version (no credentials on this host, and the task scope explicitly excludes sending prompts). The Compose worker image's and the desktop capsule's own bundled Node and Claude CLI versions were not independently checked against the new `engines.node` floor (unchanged at `>=22` either way, so low risk, but not verified for those specific asset trees). The full `@anthropic-ai/claude-agent-sdk` TypeScript source was not read beyond the `.d.ts` type surfaces and the specific vocabulary tables diffed (`filePatternTools`, `PermissionMode`, `HookEvent`, `Options.hooks`); its `bridge.mjs`/`core-*.mjs` implementation files (over 1MB each, minified) were not inspected. Whether the Claude or Kimi/Codex lanes' `mcpServers` stdio `env` list requirement changed in the `@agentclientprotocol/sdk` schema between `1.2.1` and `1.5.1` was not independently diffed (our code already always sends an explicit `env` list regardless, per `session_surface_mcp_servers`, `_acp_session.py:111-158`, so this is low-risk either way). Whether a mid-stream `usage_update` session notification is actually emitted by the Claude adapter (as opposed to only the terminal `session/prompt` `usage`/`_meta.quota` fields, which were confirmed by source) was not verified, since the live probe did not run a prompt. Discovery for this record ran without `vaultspec-rag` (the service reported stopped at `http://127.0.0.1:8766` this session); governing ADRs, plans, and the architecture-review audit were located via `vaultspec-core status`, `vaultspec-core vault list adr`, `vaultspec-core vault list plan --feature llm-context-provider-abstraction`, and targeted `rg` reads instead, and each cited record was read in full.
